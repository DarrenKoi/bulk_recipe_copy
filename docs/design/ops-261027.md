# 운영 결정: uWSGI 재기동·메모리·앱 분리 (2026-10-27)

Status: 결정 기록

SKEWNONO 저장소 세션에서 나눈 대화를 이 repo로 옮긴 기록입니다. 세 가지를
다룹니다. 전송 전용 서버의 uWSGI 설정, 재활용 옵션 없이 메모리를 관리하는 방법,
화면을 SKEWNONO에 둘지 이 앱에 둘지입니다. 결정은 `handoff.md`와 `spec.md`에
이미 반영했고(`d5bda73`), 이 문서는 그 이유와 아직 하지 않은 일을 남깁니다.

## 1. uWSGI: `touch-reload`는 수동 재기동 전용 (user-confirmed 2026-10-27)

- `touch-reload = %drestart.txt`를 둡니다. 사용자가 직접 재기동할 때 씁니다.
  `restart.txt`는 이미 `.gitignore`에 있습니다.
- **야간 자동 재기동은 없습니다.** SKEWNONO의 00:05 `uwsgi_touch_reload` 같은 job을
  이 앱에 두지 않습니다.
- 재기동은 진행 중인 전송을 끊습니다. 끊긴 file은 다음 부팅의 재기동 대조
  (`transfer.reconcile`)가 `verified`/`pending`/`uncertain`으로 다시 판정하므로
  데이터는 잃지 않습니다.
- `max-requests`·`reload-on-rss`·`harakiri`는 두지 않습니다. 셋 다 **사람이 고르지
  않은 시점**에 프로세스를 끊고, `processes=1`이라 그것은 모든 전송을 뜻합니다.
  특히 `harakiri`는 화면 요청 하나가 걸려도 worker 전체를 SIGKILL합니다. 요청이
  걸리는 문제는 앱 안의 deadline(`browse_seconds=5`, `transfer_seconds=60`)이
  코드가 붙은 오류로 끝냅니다.

| 설정 | SKEWNONO | 이 앱 | 이유 |
| --- | --- | --- | --- |
| `processes` | 4 | 1 | worker마다 스케줄러·대조가 돌면 같은 job을 두 번 보냅니다 |
| `touch-reload` | 야간 자동 + 수동 | 수동만 | 재기동 시점을 사람이 고릅니다 |
| `max-requests` | 1000 | 없음 | 요청 수와 무관하게 전송 스레드를 끊습니다 |
| `harakiri` | 720 | 없음 | SIGKILL 하나가 모든 전송을 끊습니다 |

## 2. 메모리: 재활용 대신 상한으로 묶습니다

`reload-on-rss`·`max-requests`는 메모리 관리가 아니라 누수를 주기적으로 버리는
반창고입니다. 요청이 끝나면 일도 끝나는 SKEWNONO에서는 싸지만, 이 앱에서는 "천천히
새는 메모리"를 "아무도 고르지 않은 시점에 끊기는 job"으로 바꿀 뿐입니다.

### 이미 있는 상한

전송 스레드 하나는 동시에 대략 스냅샷 바이트와 검증용 재다운로드 바이트 두 개를
쥡니다.

| 항목 | 상한 | 위치 |
| --- | --- | --- |
| 파일 하나 | `transfer_max_bytes` 64 MB, 스냅샷은 `expected + 1` 바이트까지만 읽음 | `transfer.snapshot_file` |
| 검증 다운로드 | `max_bytes` 넘으면 중단 | `transfer._compare` |
| 목록 | `browse_max_entries` 5000 | `browse.py` |
| 스레드 | `max_threads` 32 | 스케줄러 |

최악은 64 MB × 2 × 32 ≈ **4 GB**입니다. 실제 레시피 파일은 KB~수 MB라 평소에는
수십 MB입니다. 슬롯 메모리가 이보다 작으면 uWSGI 옵션이 아니라
`transfer_max_bytes`를 실제 최대 파일 크기에 맞게 낮춥니다(16 MB면 최악 1 GB).
OOM이 나도 master가 worker를 다시 띄우고 재기동 대조가 이어 가므로, OOM은 사고가
아니라 빈도를 볼 지표입니다.

이 계산은 **전송만** 셉니다. recipe tuning도 이 repo에서 진행하므로(2026-10-27,
`CLAUDE.md` "작업 분담") tuning 요청의 메모리가 같은 프로세스에 더해집니다. tuning
요청에도 행 수·바이트 상한을 두어 최악값을 계산할 수 있게 하고, 상한으로 묶이지
않으면 전송과 프로세스를 나누는 것을 검토합니다.

### 아직 하지 않은 것 (필요해지면 넣음)

| 항목 | 내용 | 넣을 때 |
| --- | --- | --- |
| `memory-report = true` | 요청이 끝날 때마다 RSS를 로그에 남깁니다. 열린 상세 화면이 몇 초마다 조회하므로 전송 중 RSS 추이가 공짜로 쌓입니다 | 사무실 첫 실측(티켓 14) 때 켜서 관찰 |
| `env = MALLOC_ARENA_MAX=2` | 여러 스레드가 크기가 다른 `bytes`를 계속 할당하면 glibc가 스레드마다 arena를 만들어, 누수 없이도 RSS가 계단식으로 오릅니다 | 위 로그에서 RSS가 내려오지 않고 오르기만 할 때 |
| 유휴 시 자가 재기동 | 돌고 있는 job이 없을 때만, RSS가 기준을 넘으면 앱이 `restart.txt`를 touch합니다. `reload-on-rss`의 안전한 버전입니다 | 유휴 상태 RSS가 계속 오르는 것이 관측될 때 |

## 3. 화면 위치: 이 앱에 둡니다 (r3 재확인, 2026-10-27)

"SKEWNONO에 화면을 두고, 이 서버는 전송만 한 뒤 결과를 SKEWNONO로 보내는" 안을
다시 검토했고, 지금 구조(이 앱이 화면까지)를 유지합니다. r2에서 폐기된 안과 같은
모양이며 이유도 같습니다. 핵심은 화면 위치가 아니라 **job 상태의 원본이 어디 있느냐**이고,
그것은 SQLite를 가진 이 앱일 수밖에 없습니다.

| 관점 | SKEWNONO 화면 + 전송 서버 | 이 앱에 화면까지 (현재) |
| --- | --- | --- |
| 상태 | SKEWNONO(`processes=4`)에 결과 저장소(Redis 쓰기)가 필요합니다 | SQLite 하나 |
| 결과 전달 | push는 SKEWNONO 재기동 중 유실되어 재시도 큐가 필요합니다 | 화면이 같은 프로세스를 직접 조회 |
| 인증 | 서버 간 토큰, 실행자 신원 중계와 위조 방지 | 같은 게이트웨이의 `LASTUSER` 쿠키 |
| 장애 결합 | 한쪽이 내려가면 화면이나 결과가 멈춤 | SKEWNONO가 내려가도 복사는 계속 |
| 배포 | 화면·로직이 두 번 배포되고 API 계약이 어긋날 수 있음 | 한 번 |
| 사용자 경험 | 한 앱 안에서 메뉴 통합 | 외부 링크 하나, 시각 언어는 복사로 맞춤 |

**다시 볼 조건:** SKEWNONO의 다른 페이지도 대량·장시간 전송을 하게 될 때(예:
tool-files 폴더 일괄 다운로드, 여러 장비 일괄 업로드)입니다. 그때는 이 서버를 공유
전송 백엔드로 넓히되 **push가 아니라 pull**로 합니다. SKEWNONO는 `/api/transfer/*`를
이 서버로 프록시만 하고 상태 원본은 이 서버의 SQLite에 둡니다. 레시피 복사 화면은
그때도 이 앱에 남깁니다.

## 배포 전 확인 (티켓 14에 추가함)

- `wsgi.ini`는 office cloud Linux에서만 적용됩니다(user-confirmed 2026-10-28). 집·사무실
  localhost 실행은 `python index.py`라 uWSGI 설정을 읽지 않습니다.
- **CPU는 1개로 시작합니다**(user-confirmed 2026-10-28). `processes=1`이라 Python
  코드는 GIL 때문에 코어를 최대 1개만 씁니다. 전송은 FTP 대기가 대부분이라 SHA-256까지
  더해도 1개로 충분합니다. 소수 할당(1.5 등)은 cgroup 할당량이고, 할당량을 다 쓰면 그
  주기 동안 프로세스 전체(전송 스레드 포함)가 멈춥니다. 전송은 실패하지 않고 느려지기만
  합니다. 컨테이너 `nr_throttled`가 계속 늘면 1.5개로 올립니다. 1.5가 limit인지
  request인지 확인합니다(throttling은 limit이 정합니다). 메모리는 CPU와 따로 2절의
  최악값으로 정합니다.
- `env = OMP_NUM_THREADS=1`을 둡니다. pyarrow·BLAS 스레드 풀은 cgroup 할당이 아니라
  호스트 코어 수로 커지고(Python 3.11 `os.cpu_count()`도 같습니다), 그러면 tuning
  계산 하나가 할당량을 먼저 소진합니다.
- `buffer-size = 32768`을 둡니다. SKEWNONO와 같은 게이트웨이를 거치므로 같은 값입니다.
  기본 4096이면 사내 쿠키가 많을 때 uWSGI가 요청을 버립니다.
- `BRC_VAR_DIR`를 번들 밖의 영구 폴더로 지정합니다. 기본값은 repo 안 `var/`라
  번들 갱신 때 SQLite와 스냅샷이 함께 사라질 수 있습니다. **로컬 디스크**여야
  합니다(SQLite WAL은 네트워크 파일시스템에서 깨집니다).
- 클라우드 `wsgi.ini`는 사용자가 직접 올리고 수정할 수 있으며, 이 repo의 `wsgi.ini`를
  최대한 그대로 따릅니다(user-confirmed 2026-10-28). 슬롯 사정으로 다르게 둘 수밖에
  없는 줄(포트 등)만 다르게 두고, 그 사본에 `harakiri`·`max-requests`·`reload-on-rss`가
  들어가지 않게 합니다. 들어가면 1·2절이 무의미해집니다.
- OFFICE-VERIFY 3(`RNTO` 덮어쓰기, `MKD`, 장비당 세션 수)은 사무실 회신 대기입니다.
- 바이트 단위 이어받기(FTP `REST`)는 두지 않습니다. 파일이 KB~수 MB라 파일 하나를
  처음부터 다시 보내도 짧고, Hitachi의 `REST STOR` 지원도 모릅니다. 파일 하나가
  100 MB를 넘기 시작하면 다시 봅니다.
