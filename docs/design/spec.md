# Spec: 레시피 횡전개 앱 `bulk_recipe_copy` v1

Status: ready-for-agent

출처는 `handoff.md` r3(2026-10-18 grilling 확정)입니다. 거기 "확정한 결정"을 그대로
옮겼고, 이 문서에서 새로 정한 것은 **(스펙 결정)**으로 표시했습니다. OFFICE-VERIFY
2·3은 가정으로 적고, 답이 다르면 바뀌는 지점을 "Further Notes"에 모았습니다.

## Problem Statement

MI 엔지니어는 매일 20~30개의 Hitachi CD-SEM 레시피를 새로 만들고, 그 대부분을 다른
장비 여러 대로 복사(횡전개)해야 합니다. 지금은 장비 FTP에 하나씩 붙어 `.idp`
파일과 raw 폴더를 손으로 옮깁니다. 장비 15대면 같은 일을 15번 반복하고, 파일 하나가
빠지거나 반쪽만 올라가도 알아챌 방법이 없습니다. 레시피는 당일 만들어져 바로
복사되므로 지연된 목록(Redis registry)으로는 찾을 수 없고, 장비 FTP를 실시간으로
봐야 합니다.

## Solution

독립 web app 하나에서 원본 장비와 class를 고르고, 레시피 여러 개와 대상 장비 여러
대를 골라 한 번에 복사합니다. 경로는 사용자가 정하지 않고 원본과 **같은 경로**에
놓습니다. 실행 전 확인 팝업이 대상의 상태(class 폴더 없음, 다른 fab에 같은 class
있음, 같은 레시피 있음)를 알리고, 실행자 본인이 확인하면 전송합니다. 올린 파일은
전부 다시 내려받아 SHA-256으로 대조하고, 결과를 장비 → 레시피 → 파일 순으로 보여
줍니다. 실패한 장비만 골라 새 job으로 다시 보낼 수 있습니다. 앱이 중간에 죽어도
다시 뜰 때 대상 장비를 읽어 대조하고 이어 갑니다.

## User Stories

### 접근

1. MI 엔지니어로서, SKEWNONO 상단 메뉴의 "레시피 복사" 링크로 앱에 들어가고 싶습니다. 평소 쓰는 도구에서 바로 찾을 수 있도록.
2. MI 엔지니어로서, 따로 로그인하지 않고 사내 신원(`LASTUSER`)으로 들어가고 싶습니다. 계정을 하나 더 관리하지 않도록.
3. 허용 목록에 없는 사용자로서, 앱이 왜 막혔는지 알려 주는 화면을 보고 싶습니다. 누구에게 요청할지 알 수 있도록.
4. 앱 운영자로서, 허용 목록을 배포 설정에서 고치고 싶습니다. 관리 화면 없이 사람을 추가·삭제할 수 있도록.

### 원본 찾기

5. MI 엔지니어로서, 명부(`sem_list`)의 Hitachi 장비 중에서 fab과 무관하게 원본 장비를 고르고 싶습니다. 레시피를 만든 장비가 어느 fab이든 시작할 수 있도록.
6. MI 엔지니어로서, 장비 ID 일부를 입력해 장비 목록을 거르고 싶습니다. 수십 대 중에서 빨리 찾을 수 있도록.
7. MI 엔지니어로서, 원본 장비의 class 목록을 보고 하나를 고르고 싶습니다. 레시피가 있는 곳으로 바로 들어가도록.
8. MI 엔지니어로서, 그 class의 레시피를 이름으로 거르고 싶습니다. 오늘 만든 레시피를 빨리 찾을 수 있도록.
9. MI 엔지니어로서, 레시피 표에서 이름(idp), 수정 시각, idw 이름을 보고 싶습니다. 같은 이름의 옛 레시피와 구별하도록.
10. MI 엔지니어로서, 수정 시각으로 정렬하고 싶습니다. 방금 만든 레시피가 위로 오도록.
11. MI 엔지니어로서, 행을 클릭하면 raw 폴더의 파일 수와 총 크기를 보고 싶습니다. 레시피가 다 만들어졌는지 감을 잡도록.
12. MI 엔지니어로서, 원본 장비에 닿지 않으면 그 사실을 바로 보고 싶습니다. 빈 목록을 "레시피 없음"으로 오해하지 않도록.

### 대상 고르기와 확인

13. MI 엔지니어로서, 레시피를 여러 개 고르고 싶습니다. 한 번에 옮기도록.
14. MI 엔지니어로서, 대상 장비를 여러 대, 다른 fab까지 고르고 싶습니다. fab을 넘는 횡전개도 한 번에 하도록.
15. MI 엔지니어로서, 원본 장비가 대상 목록에서 빠져 있기를 바랍니다. 자기 자신에게 복사하는 실수를 하지 않도록.
16. MI 엔지니어로서, `.idw` 포함 여부를 고르되 기본은 꺼져 있기를 바랍니다. 공유 파일을 모르고 덮지 않도록.
17. MI 엔지니어로서, `.idw`를 켜면 "같은 idw를 쓰는 다른 레시피도 영향받음" 문구를 보고 싶습니다. 영향 범위를 알고 켜도록.
18. MI 엔지니어로서, 대상에 같은 class 폴더가 없으면 "만들까요?"를 묻고 싶습니다. 예라면 만들고 진행하도록.
19. MI 엔지니어로서, class 폴더 생성을 거절한 장비는 이번 job에서 빠지기를 바랍니다. 나머지 장비는 그대로 진행하도록.
20. MI 엔지니어로서, 다른 fab의 대상에 같은 class 폴더가 이미 있으면 "같은 class가 있으니 주의" 경고를 보고 싶습니다. 이름만 같은 다른 공정에 섞지 않도록.
21. MI 엔지니어로서, 대상에 같은 레시피가 이미 있으면 어느 장비의 어느 레시피인지 보고 덮어쓸지 정하고 싶습니다. fab과 무관하게 의도한 덮어쓰기만 일어나도록.
22. MI 엔지니어로서, 확인 팝업에서 장비 수, 레시피 수, 파일 수, 총 크기를 보고 싶습니다. 규모를 알고 실행하도록.
23. MI 엔지니어로서, 별도 승인자 없이 내가 확인하면 바로 실행되기를 바랍니다. 당일 복사가 기다리지 않도록.
24. MI 엔지니어로서, 확인 뒤 대상에 같은 레시피가 새로 생겼다면 덮지 않고 실패로 남기를 바랍니다. 확인하지 않은 덮어쓰기가 일어나지 않도록.

### 진행

25. MI 엔지니어로서, 작업 목록에서 대기·진행 중·완료·실패를 보고 싶습니다. 여러 job을 한눈에 보도록.
26. MI 엔지니어로서, 내 job이 대기 중이면 "대기 n번째"를 보고 싶습니다. 언제 시작할지 가늠하도록.
27. MI 엔지니어로서, 장비 15대로 보내도 가장 느린 한 대의 시간 정도에 끝나기를 바랍니다. 대수가 늘어도 기다림이 늘지 않도록.
28. MI 엔지니어로서, 열어 둔 상세 화면이 몇 초마다 갱신되고 끝나면 요약이 뜨기를 바랍니다. 새로고침하지 않아도 되도록.
29. MI 엔지니어로서, 진행 중인 job을 취소하고 싶습니다. 잘못 고른 대상에 더 쓰지 않도록.
30. MI 엔지니어로서, 취소하면 지금 올리는 파일까지만 끝나고 멈추기를 바랍니다. 반쪽 파일이 남지 않도록.
31. MI 엔지니어로서, 다른 사람의 job도 목록에서 보고 싶습니다. 같은 장비를 누가 쓰고 있어 기다리는지 알도록.
32. MI 엔지니어로서, 원본 레시피가 복사 중에 바뀌고 있으면 job이 막히기를 바랍니다. 반쯤 편집된 레시피가 퍼지지 않도록.

### 결과

33. MI 엔지니어로서, 결과를 장비 → 레시피 → 파일 순으로 펼치고 싶습니다. 문제가 있는 곳까지만 들어가도록.
34. MI 엔지니어로서, 전부 검증된 장비는 한 줄로 접혀 있기를 바랍니다. 실패에 눈이 가도록.
35. MI 엔지니어로서, 일부 실패한 장비에서 어느 파일이 왜 실패했는지 보고 싶습니다. 원인을 바로 판단하도록.
36. MI 엔지니어로서, 결과가 불명확한 장비에는 "장비에서 직접 확인" 안내를 보고 싶습니다. 앱이 모르는 것을 성공으로 착각하지 않도록.
37. MI 엔지니어로서, "처리율 100%"와 "전체 성공"이 구분되어 보이기를 바랍니다. 다 처리됐지만 실패가 섞인 경우를 놓치지 않도록.
38. MI 엔지니어로서, 대상 raw 폴더에 원본에 없는 파일이 있으면 "대상에만 있는 파일 n개"를 보고 싶습니다. 남은 옛 파일을 알도록.
39. MI 엔지니어로서, 실패·불명확 장비만 골라 새 job으로 다시 보내고 싶습니다. 성공한 장비에 다시 쓰지 않도록.
40. MI 엔지니어로서, 끝난 job을 닫고 싶습니다. 목록이 정리되고 서버 임시 공간이 비도록.
41. MI 엔지니어로서, 앱 안에서만 통지를 받기를 바랍니다. 메일·Teams 알림이 쌓이지 않도록.

### 신뢰성

42. MI 엔지니어로서, 앱이 전송 중에 재기동되어도 이미 올라간 파일을 다시 쓰지 않고 이어 가기를 바랍니다. 장비에 불필요한 쓰기가 없도록.
43. MI 엔지니어로서, 재기동 뒤 확인할 수 없는 파일은 "불명확"으로 남기를 바랍니다. 추측으로 성공 처리되지 않도록.
44. 장비 담당자로서, 장비 FTP에 한 앱이 연결을 하나만 열기를 바랍니다. `msr_image` 등 다른 사용과 세션이 다투지 않도록.
45. 장비 담당자로서, 앱이 출처를 모르는 임시 파일을 지우지 않기를 바랍니다. 다른 사람의 작업이 사라지지 않도록.
46. 앱 운영자로서, 동시에 도는 전송 스레드 합의 상한을 설정하고 싶습니다. 서버와 네트워크가 넘치지 않도록.
47. 앱 운영자로서, 스냅샷 총량이 상한을 넘으면 새 job이 거부되기를 바랍니다. 디스크가 차서 앱이 죽지 않도록.
48. 개발자로서, 집에서 가짜 장비로 앱 전체를 띄우고 싶습니다. 사무실 없이 화면과 흐름을 확인하도록.

## Implementation Decisions

### 앱 모양 (확정)

- Flask가 빌드된 Nuxt 4 SPA(`ssr: false`)를 서빙합니다. SKEWNONO의 SPA 서빙, `LASTUSER` 인증, `.env`·office Redis 연결, vendored `ftp_handler`를 **복사**합니다.
- uWSGI `processes=1`, `threads=4`, `enable-threads`, `lazy-apps`. `touch-reload`·`max-requests`는 두지 않습니다.
- 앱 팩토리가 부팅 때 **스케줄러 스레드 하나**를 띄웁니다. 장비 작업자 스레드는 스케줄러가 job마다 만듭니다.
- 앱 팩토리는 세 가지를 주입받습니다: 장비 명부 공급자, `connect(장비) → FTP 클라이언트`, 저장 위치(SQLite 파일·스냅샷 폴더). 운영은 office Redis와 `FtpClient`, 테스트와 집 개발은 가짜 장비를 넣습니다. **(스펙 결정)**
- FTP 계정·인코딩·각종 상한은 `.env`에서 읽습니다. `.env`는 커밋하지 않습니다.

### 모듈

| 모듈 | 하는 일 | 겉으로 드러나는 것 |
| --- | --- | --- |
| 장비 명부 | `sem_list`를 읽기 전용으로 읽어 Hitachi 장비만(eqp_id, eqp_ip, fab_name, 모델) 돌려줌 | 장비 목록, eqp_id → 장비 해석 |
| 레시피 레이아웃 | class·idw·idp에서 레시피 구성 경로를 계산하는 순수 함수 | idp 파일, raw 폴더, 옵션 idw 파일의 경로 |
| 원본 탐색 | class 목록, 레시피 목록(LIST 1회), raw 폴더 요약 | 화면 2단계의 표 |
| 사전 점검 | 대상마다 class 폴더·레시피·idw 존재를 읽기만으로 확인 | 확인 항목 목록 |
| job 저장소 | SQLite에 job·file 행 기록, 상위 상태 집계 | job 목록, 결과 트리 |
| 스케줄러 | FIFO 큐, 장비 겹침 대기, 스레드 상한 | 대기 순번, job 시작 |
| 스냅샷 수집 | 원본을 job당 한 번 읽어 로컬 폴더와 manifest로 | manifest(상대 경로·크기·SHA-256) |
| 장비 작업자 | 대상 한 대에 연결 하나로 파일을 순차 전송·검증 | file 상태 전이 |
| 대조 복구 | 기동 시 미완료 file을 대상과 대조 | file 상태 재판정 |
| FTP 클라이언트 확장 | `put` 덮어쓰기 모드, `mkdir` | vendored·upstream 양쪽 |

레시피 레이아웃 모듈 하나에 OFFICE-VERIFY 2의 답이 모입니다. 다른 모듈은 경로를 직접
조립하지 않습니다. **(스펙 결정)**

### 레시피의 정의 (확정, 레이아웃은 가정)

```text
/HITACHI/DEVICE/HD/{class_name}/data/{idw}/
    ├── {idp}.idp     ← 항상 포함
    └── {idp}/        ← raw 폴더, 항상 포함 (하위 전체)
{idw}.idw             ← idp보다 상위, 옵션(기본 끔)
```

- 가정: `.idw`는 `data/` 바로 아래(`data/{idw}.idw`)에 있습니다. raw 폴더는 하위
  폴더까지 전부 복사하고 제외할 파일은 없습니다.
- 대상 경로는 원본 경로와 같습니다. 사용자 설정이 없습니다.

### 원본 탐색

- class 목록은 `/HITACHI/DEVICE/HD`의 하위 폴더입니다.
- 레시피 목록은 `data/` 아래를 **LIST 1회**로 얻어 `(idw, idp, 수정 시각)` 행을
  만듭니다. 가정: 그 한 번의 목록(재귀 LIST 또는 와일드카드)으로 `data/{idw}/{idp}.idp`가
  보입니다. 이름 거르기는 서버가 아니라 그 결과에서 합니다.
- 파일 수·총 크기는 행을 열 때 raw 폴더를 LIST해 계산합니다.
- 탐색은 화면 요청 스레드에서 짧은 timeout으로 합니다. 전송 연결과 별개입니다.

### 사전 점검과 확인

- 입력: 원본 장비, class, 레시피 목록, 대상 장비 목록, idw 포함 여부.
- 대상마다 읽기만 합니다. 결과 항목은 셋입니다.
  - `class_missing`: 대상에 class 폴더가 없습니다. 사용자가 예/아니오를 고릅니다. 아니오면 그 대상은 job에서 빠집니다.
  - `class_exists_other_fab`: 원본과 fab이 다른 대상에 같은 class 폴더가 있습니다. 경고만 하고 진행합니다.
  - `recipe_exists`: 대상에 같은 `{idp}.idp` 또는 `{idp}/`가 있습니다(idw를 켰으면 `.idw` 포함). 덮어쓰기를 허락받습니다. 허락하지 않은 (대상, 레시피) 쌍은 job에서 빠집니다.
- job 생성 요청은 사전 점검 결과와 사용자의 선택을 함께 보냅니다. 서버는 job에
  **덮어쓰기를 허락받은 (대상, 레시피) 쌍**과 **폴더를 만들어도 되는 대상**을 기록합니다. **(스펙 결정)**
- 전송 때 허락받은 쌍만 덮어쓰기 모드를 씁니다. 나머지는 일반 `put`이라, 확인 뒤
  대상에 새로 생긴 파일은 `TargetExists`로 `failed`("확인 뒤 대상에 생김")가 됩니다. **(스펙 결정)**
- 실행자 본인의 확인이 전부입니다. 승인자는 없습니다.

### 쓰기 규칙 (확정)

- 쓰기 경로는 `FtpClient.put`(임시 이름 STOR → `RNTO`) 하나입니다.
- 덮어쓰기 모드: 임시 업로드 → 기존 파일 `DELE` → `RNTO`. 가정은 "RNTO가 기존 파일을 덮지 않을 수 있다"이므로 항상 `DELE`를 먼저 합니다.
- `mkdir`: class 폴더(`{class}/`, `{class}/data/`), `data/{idw}/`, raw 폴더와 그 하위 폴더를 만듭니다. 이미 있으면 성공으로 봅니다. 가정: `MKD`는 한 단계씩만 됩니다.
- 대상 raw 폴더에서 원본에 없는 파일은 지우지 않고 개수만 셉니다.
- fleet `upload`(덮어쓰는 STOR)와 `BackgroundJobs`는 쓰지 않습니다.
- `put`·`mkdir` 변경은 vendored 사본과 upstream `flask_modules`에 같이 넣습니다.

### 상태 모델 (확정)

- 단위: job → target(장비) → recipe → file. **상태는 file에만** 있고 위는 집계합니다.
- file 키: `(job_id, target_eqp, destination_path)`. 행에 기대 크기·SHA-256, 실패 사유, `uncertain`일 때 임시 파일 경로를 둡니다.
- file 상태: `pending → in_progress → verified | failed | uncertain`.
- job 행: 실행자, 확인 시각, 원본 장비, 대상 장비, idw 포함 여부, 허락받은 덮어쓰기 쌍,
  폴더 생성 허락 대상, manifest 해시, 스냅샷 폴더, 취소 플래그, 닫힘 여부.
- 예외 하나: file 행은 스냅샷 수집 뒤에 생기므로, 그 전 단계는 job 행의 **수집 결과**
  필드(`대기 | 수집 중 | 완료 | 차단(사유)`)로 나타냅니다. **(스펙 결정)**
- 장비별 결과 집계: `uncertain`이 하나라도 있으면 **불명확**, 아니고 `failed`가 있으면
  **일부 실패**, 전부 `verified`면 **전부 검증됨**. 불명확을 앞에 두는 것은 사람이 직접
  확인해야 하는 쪽이기 때문입니다. **(스펙 결정)**
- job 집계: 처리율(`pending`·`in_progress`가 아닌 file의 비율)과 성공 여부(전부 `verified`)를 따로 냅니다.
- 취소: 장비 작업자가 파일 사이마다 플래그를 봅니다. 남은 `pending`은 `failed`("취소")가
  됩니다. 그래서 재시도 흐름에 그대로 실립니다. `paused`는 없습니다. **(스펙 결정)**

### 스냅샷 수집 (확정)

- job이 시작되면 원본 장비에 연결 하나로 레시피 전부를 로컬 스냅샷 폴더에 받습니다.
- 수집 전후 목록(경로·크기·mtime)을 비교합니다. 다르면 한 번 더 수집하고, 또 다르면
  job을 **차단**합니다(수집 결과 = 차단, 사유 "원본이 바뀌는 중"). 이 비교는 **탐지이지
  증명이 아닙니다.** 두 목록 사이에 같은 크기·mtime으로 바뀐 파일은 잡지 못합니다.
- 수집이 끝나면 manifest를 만들고 file 행을 대상 × 파일만큼 `pending`으로 만듭니다.
- 총량 상한(기본 20 GB)을 넘으면 새 job 생성을 거부합니다.
- 스냅샷 삭제: 전부 `verified`로 끝난 job은 즉시, 그렇지 않은 job은 사용자가 닫을 때.

### 장비 작업자 (확정)

- **대상 장비당 스레드 1개·FTP 연결 1개.** job의 대상 전부가 동시에 돕니다. 한 장비 안에서 파일은 순차입니다.
- 파일 하나의 순서: 필요한 폴더 `mkdir` → `put`(허락받은 쌍이면 덮어쓰기 모드) →
  같은 경로를 다시 내려받아 SHA-256 대조 → `verified` 또는 `failed`("해시 불일치").
- `TransferUncertain`(rename 응답 유실)은 `uncertain`이 됩니다. 임시 경로를 기록하고 지우지 않습니다.
- 연결이 끊기면 다시 연결해 같은 파일부터 이어 갑니다. 재시도 횟수를 넘기면 그 장비의 남은 파일은 `failed`("연결 실패")입니다.
- 레시피 하나의 파일을 다 보낸 뒤 대상 raw 폴더를 LIST해 "대상에만 있는 파일" 수를 기록합니다.
- 전송별 크기·시간·재시도 상한과 job 총 바이트 상한을 설정값으로 둡니다. 초기값은
  ADR 0001의 파일 프로파일(KB~수 MB)에 맞춰 구현 때 정합니다.
- 검증 근거는 재다운로드 SHA-256뿐입니다. SIZE·mtime·응답 코드는 증거로 쓰지 않습니다.

### 스케줄러 (확정 + 규칙 구체화)

- 큐는 확인 시각 순 FIFO입니다.
- job J는 다음을 모두 만족할 때 시작합니다. **(스펙 결정: 확정 문장을 판정 규칙으로 옮김)**
  1. J보다 앞선 미완료 job(대기 중 포함) 중 J와 장비(원본이든 대상이든)가 겹치는 것이 없습니다.
  2. J의 대상 수가 남은 스레드 예산(설정값, 기본 32) 안에 듭니다.
  3. J보다 앞서 예산 때문에 기다리는 job이 없습니다. 뒤 job이 앞지르지 않게 하려는 것입니다.
- 대상 수가 스레드 상한보다 많은 job은 생성 때 거부합니다.
- "대기 n번째"는 J보다 앞선 미완료 job 중 아직 시작하지 않은 것의 수 + 1입니다.
- 스케줄러 상태는 메모리에만 두고, 기동 때 미완료 job을 확인 시각 순으로 다시 읽어 만듭니다.

### 재기동 대조 복구 (확정)

- 기동 시 `in_progress`를 전부 `uncertain`으로 봅니다.
- 그 file과 기존 `uncertain` file마다 대상을 읽어 manifest의 해시와 같으면 `verified`,
  다르거나 없으면 `pending`으로 되돌립니다. 대상을 읽지 못하면 `uncertain` 그대로입니다.
- 출처를 모르는 임시 파일을 일괄 삭제하지 않습니다.
- 스냅샷 폴더가 사라진 job은 원본을 다시 수집합니다. 새 manifest 해시가 기록된 것과
  같으면 `pending`부터 이어 가고, 다르면 남은 `pending`을 `failed`("job 확인 뒤 원본이
  바뀜")로 둡니다. 섞인 버전이 퍼지지 않게 하려는 것입니다. **(스펙 결정)**

### 권한 (확정)

- 신원은 `LASTUSER` 쿠키입니다. 없으면 401입니다.
- MI 엔지니어 허용 목록을 `.env`에 둡니다. 목록에 없으면 앱 전체가 403이고 SPA는 안내 화면을 보여 줍니다.
- 허용된 사용자는 모든 job을 볼 수 있습니다. 취소·닫기는 실행자 본인만 합니다. **(스펙 결정)**

### HTTP API (스펙 결정)

모두 JSON이고 `/api` 아래에 있습니다. 재시도는 별도 엔드포인트가 아니라, 결과 화면이
고른 장비로 사전 점검 → job 생성을 다시 부르는 것입니다.

| 메서드 | 경로 | 하는 일 |
| --- | --- | --- |
| GET | `/api/me` | 신원과 허용 여부 |
| GET | `/api/tools` | Hitachi 장비 목록 |
| GET | `/api/tools/{eqp}/classes` | class 목록 |
| GET | `/api/tools/{eqp}/classes/{class}/recipes` | 레시피 목록(idw, idp, 수정 시각) |
| GET | `/api/tools/{eqp}/classes/{class}/recipes/{idw}/{idp}` | raw 폴더 파일 수·총 크기 |
| POST | `/api/preflight` | 사전 점검 항목 |
| POST | `/api/jobs` | 사전 점검 결과 + 선택으로 job 생성 |
| GET | `/api/jobs` | job 목록(집계, 대기 순번, 수집 결과) |
| GET | `/api/jobs/{id}` | 장비 → 레시피 → 파일 결과 트리 |
| POST | `/api/jobs/{id}/cancel` | 취소 플래그 |
| POST | `/api/jobs/{id}/close` | 닫기와 스냅샷 삭제 |

- 장비에 닿지 않으면 탐색 API는 502와 사유를 돌려줍니다. 빈 목록으로 숨기지 않습니다.
- `/api/jobs` 생성은 사전 점검 이후 상태가 바뀌었는지 다시 보지 않습니다. 그 차이는 전송 때 `TargetExists`로 드러납니다.

### 화면

- 장비 선택 → class·레시피 표 → 대상 선택 → 확인 팝업 → 작업 목록 → 결과 상세.
- 상세 화면은 열려 있는 동안 몇 초마다 `GET /api/jobs/{id}`를 부르고, 끝나면 요약을 띄웁니다.
- 시각 언어는 SKEWNONO의 `DESIGN.md`와 `--sk-*` 토큰을 복사해 씁니다.

## Testing Decisions

### 좋은 테스트

- 바깥에서 보이는 행동만 시험합니다: HTTP 응답과, 가짜 장비에 남은 파일입니다. SQLite
  테이블 모양, 스레드 구성, 내부 함수 호출은 시험하지 않습니다.
- 테스트 이름은 행동을 문장으로 씁니다(SKEWNONO vendored `ftp_handler` 테스트의 관례).

### 주 seam: HTTP API + 주입된 가짜 장비

- Flask test client로 앱 팩토리를 만들고, 가짜 장비 명부, 메모리 가짜 장비(장비별 파일 트리), `tmp_path`의 SQLite·스냅샷 폴더를 넣습니다.
- 백그라운드 스레드 대신 "큐가 빌 때까지 처리" 동기 hook을 씁니다. 이 모드에서 장비
  작업은 순차로 돕니다. 병렬성 자체는 시험하지 않고 스케줄 판정(누가 시작하고 누가
  몇 번째로 기다리는지)만 시험합니다.
- 가짜 장비가 넣을 수 있는 장애:
  - rename 응답 유실 → `uncertain`
  - 전송 중 연결 끊김, 재시도 소진
  - `RNTO`가 기존 파일을 덮는 서버와 거부하는 서버 (OFFICE-VERIFY 3 양쪽)
  - 수집 중 원본 변경 → 재수집, 두 번째도 바뀌면 차단
  - 다운로드 내용 변조 → 해시 불일치
  - 확인 뒤 대상에 레시피가 새로 생김 → `TargetExists`
- 재기동 복구는 같은 SQLite와 같은 가짜 장비 위에 앱을 **다시 만들어** 시험합니다.
  `in_progress`로 멈춘 file이 대상 상태에 따라 `verified`·`pending`·`uncertain`으로 갈립니다.
- 시험할 행동 목록: 레시피 정의(idp + raw 전체, idw 옵션), 사전 점검 세 항목, 폴더 생성
  거절 시 대상 제외, 덮어쓰기 허락 범위, 해시 검증, 장비별 결과 집계와 처리율·성공 구분,
  대상에만 있는 파일 수, 취소, 스케줄러 세 규칙과 대기 순번, 스냅샷 총량 상한 거부,
  스냅샷 삭제 시점, 허용 목록 401/403.
- 같은 가짜 장비를 집 개발 실행에도 씁니다(샘플 레시피를 채운 장비 몇 대).

### 보조 seam: `FtpClient` 확장

- `put` 덮어쓰기 모드와 `mkdir`은 로컬 FTP 서버(pyftpdlib)를 상대로 시험합니다. 실제
  `ftplib` 왕복과 응답 코드 처리를 보는 유일한 자리입니다.
- 시험할 것: 새 파일 `put`, 덮어쓰기 모드로 기존 파일 교체, 일반 `put`의 `TargetExists`,
  `mkdir`의 이미 있음 처리, 중첩 폴더 생성.

### 시험하지 않는 것

- 프론트엔드 단위 테스트는 v1에 두지 않습니다. API 계약이 시험면이고, 화면은 가짜 장비로 띄워 손으로 확인합니다.
- office Redis, 실제 장비 FTP는 자동 테스트에 넣지 않습니다. 사무실 클라우드에서 손으로 확인합니다.

### OFFICE-VERIFY 답이 다르면 바뀌는 지점

| 질문 | 가정 | 다르면 |
| --- | --- | --- |
| 2. `.idw` 위치 | `data/{idw}.idw` | 레시피 레이아웃 모듈의 경로 하나만 바뀝니다. |
| 2. raw 폴더 내용 | 하위 전체, 제외 파일 없음 | 레이아웃 모듈에 제외 규칙을 코드로 고정합니다. 사용자 설정은 두지 않습니다. |
| 2. 레시피 목록 LIST 1회 | 재귀/와일드카드 LIST 한 번으로 `data/*/*.idp`가 보임 | 원본 탐색이 idw 폴더마다 LIST하게 됩니다(왕복 N+1). 표의 열은 같습니다. |
| 3. `RNTO`가 기존 파일을 덮는가 | 덮지 않을 수 있음 → 항상 `DELE` 후 `RNTO` | 덮는다면 `DELE`를 빼서 파일이 없는 순간을 없앨 수 있습니다. 선택 사항이며 v1을 막지 않습니다. |
| 3. `MKD` 가능 여부 | 되며 한 단계씩 | 안 되면 class 폴더 생성 확인 항목이 "대상에 class 폴더 없음 → 그 장비 제외"로 바뀝니다. 중첩이 되면 단계 수만 줄어듭니다. |
| 3. 디렉터리 위로 `RNTO` | 거부 | 받아들이면 `put`의 존재 검사에 "같은 이름의 폴더" 확인을 더합니다. |
| 3. 장비당 세션 상한 | 앱 1 + `msr_image` 1이 들어감 | 1뿐이면 같은 장비를 쓰는 다른 도구와 겹칠 때 연결 실패가 납니다. 재시도 상한 안에서 `failed`로 드러납니다. |
