# 05: 전송과 검증

**What to build:** 수집이 끝난 job이 대상 장비마다 스레드 1개·FTP 연결 1개로 파일을 순차로
올리고, 같은 경로를 다시 내려받아 SHA-256으로 대조합니다. 충돌이 없는 대상으로의 복사가
끝까지 됩니다. 덮어쓰기 허락이 없는 경우(이 티켓에선 전부)는 첫 쓰기 전 재확인으로 보호합니다.

**Blocked by:** 02, 04

**Status:** ready-for-agent

- [ ] 파일 하나의 순서: 필요한 폴더 `mkdir` → 올리기 직전 해시(스냅샷 바이트를 메모리로 읽어 manifest와 비교, 같은 바이트를 `put`에) → `put` → 재다운로드 SHA-256 → `verified` 또는 `failed("해시 불일치")`
- [ ] 올리기 직전 해시가 다르거나 파일이 없으면 원격 쓰기 없이 그 job의 남은 `pending`이 `failed`(재수집은 12에서)
- [ ] 첫 쓰기 전 재확인: 대상에 `.idp`나 raw 폴더가 이미 있으면 그 (대상, 레시피) 쌍은 쓰지 않고 `failed("확인 뒤 대상에 생김")`. 조회 실패는 "없음"이 아님
- [ ] `TransferUncertain`은 `uncertain`, 임시 경로 기록, 지우지 않음
- [ ] 연결이 끊기면 재연결해 같은 파일부터. 재시도 상한을 넘기면 그 장비의 남은 파일은 `failed("연결 실패")`
- [ ] job의 대상들이 동시에 돎(운영). 동기 hook에선 순차
- [ ] pytest: 가짜 장비 끝에서 파일이 바이트 그대로 있음, 해시 불일치, 손상된 스냅샷이면 대상 무변경, raw 폴더만 생긴 대상은 쌍 전체 `failed`, rename 응답 유실 → `uncertain`, 연결 끊김과 재시도 소진
